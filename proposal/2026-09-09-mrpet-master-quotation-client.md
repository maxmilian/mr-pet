### 2.5 V1 範圍界線（引擎 ② 明確移出 V1 的項目）

引擎 ② 的規格書共 37 節，V1 不做完全部。以下六項明確移出，**此清單須列為合約附件**：

| 移出項目 | 規格書原文 | V1 實作 | 對營運的影響 |
|---------|----------|--------|-------------|
| Partial Reversal | 部分反沖 + Admin Adjustment | 僅完整反沖（整筆作廢後重開） | 院所改單需整筆重來，作業稍繁瑣 |
| Statement 狀態機 | 六態 + 跨月 Adjustment + RECONCILED | 三態（DRAFT／CONFIRMED／PAID） | 跨月調整以人工註記處理 |
| Admin Control Center | 11 模組 | 6 模組 | 報表、批次工具、進階設定 Phase 2 補 |
| RBAC 角色 | 五角色 | 三角色（Mr.Pet Admin／院所管理者／院所操作員） | 財務與稽核角色暫由 Admin 兼任 |
| 防弊告警 | 6 條規則 | 3 條核心規則 | 涵蓋短時間重複核銷、單筆異常高額、單日超限 |
| 驗收案例 | 第 36 節完整 | 主流程 + 關鍵邊界（見下） | — |

**引擎 ② 驗收基準**：

1. 同一飼主同時在兩家院所發起 Quote → 點數不得超扣
2. Confirm 重送相同 Idempotency Key → 只成立一筆
3. Ledger 重算餘額 = Wallet balance（連續 10 日零差異）
4. 完整反沖後，Wallet、Ledger、SettlementLine 三方一致
5. 月結彙總金額 = 當月 SettlementLine 加總

## 三、交付節奏

### 3.1 依賴關係

```
S1 API 契約 ──┬──> ② VetPoint（W1 Schema 依附共用層）
              ├──> ① 引擎（E7 接 Pet ID／Consent）
              └──> ③ 引擎（P1 接 Identity／Consent）

S4 Clinic ID ────> E4 院所搜尋 ────> E5 線上預約
S7 Notification ─> E5 確認簡訊、E6 報告 Email
S8 Storage ──────> P7 影像上傳 ────> E6 報告查閱
P8 Approve ──────> E6 會員中心 second opinion
② Settlement ────> （獨立，不阻擋 ①③）
```

**唯一的硬阻塞是 S1（API 契約）**。契約定稿後三引擎即可並行，不需等整個共用層完工。

這就是我們建議的 **Thin Platform 策略**：共用層第一版只做三引擎當下真的會用到的能力，不預先建造沒有使用者的抽象層——後者是共用層專案最常見的失敗模式，會先燒掉數週卻沒有任何可驗證的產出。是否採此策略請見 §五 第 1 項。
