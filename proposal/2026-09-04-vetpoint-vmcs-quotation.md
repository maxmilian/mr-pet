## 一、範圍認定：這不是「點數功能」，是清算系統

規格書第 37 節已定調——Mr.Pet V1 是三個引擎：

```
① Subscription Commerce Engine  →  ② VetPoint Medical Clearing System  →  ③ PetRisk.ai CDS
   （會員付錢給 Mr.Pet）              （權益轉換成醫療折抵與院所應收）        （病例與 Second Opinion）
```

**本報價僅涵蓋 ②**。① 與 ③ 依原提案 v1.2 另計。

原提案 §3.3.3 的「PetPoint 引擎」僅估 1.5 週（累點／折抵／查詢 API），對應的是**單向扣點**。本規格新增的是一整套雙邊清算：Ledger 不可竄改、Point Reservation 防併發、Atomic Transaction 三表同交易、Reversal、月結對帳、Rule-based 防弊、RBAC 與稽核。工作量差距仍達數倍，故獨立報價。

## 三、交付方案：單階段 12 週，第 6 週產出 Pitch Demo

3 個月的期程不足以再切兩階段（每個階段的 UAT／部署／驗收會議會多吃 3~4 人日純管理成本）。改採**單階段開發、中途插入 Demo 里程碑**。

### 3.1 交付節奏

| 階段 | 週次 | 產出 |
|-----|------|------|
| 規格凍結 | W0 | 資料模型定稿、API 契約 |
| 垂直切片 | W1–W6 | 主流程從頭到尾跑通 → 🚩 **Pitch Demo** |
| 深度硬化 | W7–W10 | 效期、併發、反沖、稽核、防弊、串接 |
| 清算與交付 | W11–W12 | 月結對帳、UAT、上線 → 🚩 **V1 上線** |

### 3.2 第 6 週 Demo 的定位與界線

Demo 走完整條 vertical slice，在台上可以完整演示：

```
飼主 PWA 看到點數餘額 → 院所端輸入折抵金額 → 產生 Quote 並保留點數
  → 飼主手機收到確認 → 確認扣點 → 院所端即時看到入帳與應收
```

**Demo ≠ 可上線**，以下必須向投資人／合作院所說明白：

- 跑在**獨立 demo 環境**，資料為測試資料，與 production 完全隔離
- 尚未包含：點數效期 FIFO、跨院併發防護壓測、反沖、稽核與防弊、月結
- UI 為功能版，視覺精修在 W7–W10 期間同步進行

拿這個去 pitch 的價值在於「不是簡報，是能操作的系統」，這一點在 6 週內是做得到的；但若對方要看的是完整清算與治理，那要等 12/12。

### 3.3 驗收基準

V1 驗收以規格第 36 節的**主流程案例 + 以下關鍵邊界**為準：

1. 同一飼主同時在兩家院所發起 Quote → 點數不得超扣
2. Confirm 重送相同 Idempotency Key → 只成立一筆
3. Ledger 重算餘額 = Wallet balance（連續 10 日零差異）
4. 完整反沖後，Wallet、Ledger、SettlementLine 三方一致
5. 月結彙總金額 = 當月 SettlementLine 加總

### 4.1 上線後的限額試營運（不另計費）

12/12 上線後不建議直接全面開放。建議首 2 週：

- 只開 **1 家種子院所**，單筆折抵上限先壓 NT$500、設每日總額上限（限額本就在 W11 Config 範圍內）
- 每日人工對帳一次（Ledger 重算 vs. Wallet balance）
- 連續 10 天零差異，才解除限額並開放其他院所

這不加開發工時，但把「金融核心有 bug」的曝險從全院所縮到一家。

### 4.2 時程風險

55 人日／12 週對單一主力人力**幾乎滿載，沒有 buffer**。因此：

- §6 的規格缺口（尤其第 1、2、3 項）**必須在簽約前有答案**，不能拖進 W0
- W0 只有 3 天，僅供資料模型定稿，不是需求討論期
- 任何規格變更直接吃時程，走 §9 變更管理

## 六、開發前必須確認的事項（規格缺口）

規格書已經非常完整，以下十項是**動工前必須有答案**的，否則會在開發中期造成返工。標 🔴 者影響架構決策，在 12 週壓縮時程下**必須於簽約前完成**。

| # | 事項 | 規格現況 | 需要的決定 |
|---|------|---------|-----------|
| 1 | 🔴 **法遵定位** | 1 點 = NT$1、可 100% 折抵、Mr.Pet 現金清算給院所 | 這已經不是「折扣點數」，而是可清算的債權，性質接近儲值。**需先取得法律意見**確認是否落入電子支付／電子票證管理條例。原提案 §7 的規避策略在本規格下不再成立 |
| 2 | 🔴 **發票與稅務** | 未定義 | 折抵的 NT$800 在院所端算不算銷售額？Mr.Pet 付院所的清算款，院所要不要開發票給 Mr.Pet？直接決定 SettlementLine 要不要帶稅務欄位 |
| 3 | 🔴 **折抵單位互斥** | 第八節「100 點起、100 為單位、無上限」vs. 第十節「輸入 800」「MVP 允許 100% 折抵」 | 兩處描述不一致，需定案（建議：100 點為級距、上限 = min(可用點數, Eligible Fee)） |
| 4 | **退費回補** | 第十七／十八節只談院所輸錯的反沖 | 若醫療服務退費，VetPoint 是否回補？回補的點數用**原到期日**還是重新計算？（建議沿用原到期日，否則可無限展期） |
| 5 | **Encounter 歸屬** | 第三一節要求 Redemption 對應 Encounter | Encounter ID 由 PetRisk.ai 產生還是 VetPoint 產生？若 PetRisk.ai 尚未上線，V1 需允許 nullable |
| 6 | **飼主無法確認的備援** | 第十二節提及 QR／PIN，未展開 | 飼主沒帶手機／不會操作時，院所可否代操作？代操作的風控與稽核如何設計（此處是最容易出弊端的環節） |
| 7 | **點數到期的會計處理** | 第六節有 EXPIRE entry | 已發出的點數在帳上是否認列為負債？到期時要不要沖銷？影響財報與 Statement 呈現 |
| 8 | **日結與爭議 SLA** | 只定義月結 | 院所若對某筆核銷有異議，多久內須提出？月結關帳後的爭議如何處理（V1 無 Adjustment，需定人工流程） |
| 9 | **多寵物 Wallet 權責** | 第七節：會員層級單一 Wallet，交易帶 pet_id | pet_id 僅為標記，不做額度隔離——需向院所端明確說明，避免「這隻的點數怎麼被那隻用掉」的客訴 |
| 10 | **Reservation TTL 值** | 第十一節建議 5 分鐘 | 院所實際作業（等飼主掏手機、找老花眼鏡）可能超過 5 分鐘。建議 15 分鐘並提供院所端「延長一次」按鈕 |

> 第 1、2 項若結論改變，系統定位與部分模組需重估，屆時本報價與時程一併重議。

## 七、前提假設與不含項目

### 7.1 假設

1. VetPoint 資料庫使用 **Cloud SQL PostgreSQL**（依規格第 28 節），由客戶 GCP 帳號承擔費用
2. 身份層沿用原提案的 **Clerk SSO**，本報價不含 IdP 建置
3. Subscription（發點來源）與 Encounter（看診回饋來源）由對方系統提供 **REST API 或 Webhook**；若需由安璣一併開發，另計
4. 院所端與 Admin 為 **Web 應用**（RWD），不含原生 App
5. 設計稿由客戶提供，或沿用現有 `mrpet.tw` 設計規範；不含獨立 UI/UX 設計工時
6. 客戶方需指派 **1 名決策窗口**，於 W0 與各里程碑 3 個工作日內回覆確認

### 7.2 不含項目
